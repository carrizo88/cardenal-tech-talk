# Relevar el repositorio

Entrada: proyecto actual, sin feature requerida.
- Inspeccionar selectivamente README, manifiestos, estructura, configuración de ejemplo, modelos y puntos de entrada. Excluir secretos, builds y memorias ajenas. No recorrer node_modules en masa: consultar solo paquetes identificados y pertinentes según el paso de dependencias.
- Registrar propósito y usuarios del producto, capacidades implementadas y pendientes documentadas; stack, arquitectura, módulos, datos, autenticación, modos de ejecución, pruebas y límites operativos. Distinguir declaraciones de README de evidencia de código; resolver contradicciones con preguntas concretas.
- Guardar fuentes y hechos en .cardenal/repository-context.json: schemaVersion 1, sources, facts, questions según la guía de contexto, sin change. Un hecho observado de producto puede estar sustentado por documentación o código; no requiere inventar una decisión del usuario. Las propuestas permanecen propuestas.
- Preguntar solo dudas necesarias para comprender el repositorio. La falta de una feature, criterios de aceptación de un cambio o entorno para futuras escrituras no son bloqueos de este relevamiento.
- Registrar como comportamiento vigente lo que código y documentación respaldan consistentemente. No pedir reconfirmación ni ofrecer alternativas (por ejemplo OR/AND) sin una contradicción concreta, evidencia faltante relevante o solicitud de cambio. Citar las fuentes que discrepan cuando exista una contradicción. Las decisiones sobre rediseño corresponden a `/feature`, no a este relevamiento. No hay una cantidad mínima de preguntas; questions puede quedar vacío.
- No sobrescribir context.json ni board.json, no elegir roles de implementación y no cambiar ramas. No ejecutar escrituras externas ni migraciones.
- Completar doc/public/README.md como índice y doc/public/funcionalidades.md con todas las funcionalidades observadas, actores, propósito, flujos, reglas y límites en lenguaje de producto. Si crece, crear fichas .md por funcionalidad y enlazarlas. Diferenciar implementado, parcial y pendiente; no documentar una propuesta como entregada.
- Completar doc/tech/README.md, sistema.md y fichas técnicas .md por funcionalidad: dominio, contratos, autenticación, permisos, datos, integración, errores y escenarios, con rutas y fuentes observadas. No incluir credenciales ni publicar información de bibliotecas del cliente en doc/public. Los documentos Markdown son referencia permanente para los agentes y SDD; los JSON internos viven en .cardenal.
- Relevar dependencias desde manifiestos, lockfiles e imports antes de leer paquetes. Crear doc/tech/dependencies/README.md y resúmenes breves por dependencia relevante (por ejemplo Auth0 o Supabase si existen): propósito en ESTE proyecto, versión observada, módulos que la usan, configuración por nombre sin valores, contratos y límites. No inferir uso solo por estar instalada.
- Preguntar en el relevamiento inicial, salvo respuesta vigente: «¿Hay alguna biblioteca propia del cliente o dependencia que requiera consideración especial?». Ante una dependencia desconocida o poco habitual, preguntar si es custom, para qué se usa y cuán extendido es su uso; no clasificarla como propia por desconocerla. Registrar dudas y continuar lo independiente.
- Para bibliotecas propias confirmadas o dependencias cuyo contrato no se entienda desde el proyecto, consultar selectivamente su README, package.json, tipos o entrypoints en node_modules (si están disponibles). No instalar ni ejecutar paquetes para explorarlos por defecto, ni leer todo el árbol. Si una biblioteca del cliente es confidencial, resumirla solo en doc/private/dependencies; las compartibles van a doc/tech/dependencies; citar ruta y versión observadas. Si faltan archivos, registrar el límite sin inventar APIs.
- Los índices deben enlazar las fichas completadas. La CLI solo crea esqueletos: /inicializate debe completarlos desde fuentes y señalar los pendientes reales antes de declarar el relevamiento terminado.
Salida: contexto compartido del repositorio, fuentes y dudas explícitas. Ejecutar validate-repo. Ready indica consistencia del relevamiento, no conocimiento exhaustivo ni autorización para implementar. Terminar indicando `/feature <necesidad>` y guardar checkpoint local.
